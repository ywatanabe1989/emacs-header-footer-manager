## Worktree Guidelines for Multiple Agents Collaboration

## Benefits of Using Git Worktrees
- Work on multiple branches simultaneously without switching contexts
- Enables parallel development by different agents on separate features
- Shares the same repository objects with minimal disk space overhead
- Avoids the need withouth changes when switching between tasks

## Basic Worktree Commands

``` bash
## Create a new worktree for an existing branch
git worktree add ../path-to-new-directory branch-name

## Create a new branch with a new worktree
git worktree add -b new-branch-name ../path-to-new-directory

## List all worktrees
git worktree list

## Remove a worktree when done
git worktree remove ../path-to-new-directory
```

## Recommended Workflow for Multiple Agents

1. Main repository stays on `main` branch
2. Each agent works in their own worktree with a feature branch: `agent-01-feature-name`
3. Use descriptive branch names with agent identifiers: `agent-01/feature-name`
4. Pull changes from remote before creating new worktrees
5. Periodically update worktrees with changes from main branch

## Agent-Specific Workflow

### Setting Up Agent Worktrees
1. Create a dedicated directory structure for agents:
   ```
   git worktree add -b agent1/feature-name ../repo-agent1 
   git worktree add -b agent2/feature-name ../repo-agent2
   ```

2. Naming convention for branches:
   - Format: `agent<ID>/<feature-description>`
   - Examples: `agent1/implement-login`, `agent2/fix-ui-elements`

3. Directory naming convention:
   - Format: `../repo-agent<ID>` or `../repo-agent<ID>-<feature>`
   - Examples: `../repo-agent1`, `../repo-agent2-login`

### Collaborative Development Process

1. Initial setup:
   ```
   # From main repository
   git worktree add -b agent1/feature ../repo-agent1
   ```

2. Agent work procedure:
   - Each agent only works in their assigned worktree
   - Each agent commits to their own branch
   - No direct commits to main branch

3. Merging workflow:
   - Agent completes feature in their branch
   - Code review is performed
   - Main repository pulls and merges the agent's branch
   - Other agents update their worktrees with the new changes

### Synchronization Between Agents

1. Agent-to-agent communication:
   - When agent1 needs agent2 to have their changes:
   ```
   # Agent1 pushes their branch
   cd ../repo-agent1
   git push origin agent1/feature
   
   # Agent2 fetches and merges Agent1's work
   cd ../repo-agent2
   git fetch origin
   git merge origin/agent1/feature
   ```

2. Main repository integration:
   ```
   # From main repository
   git fetch origin
   git merge origin/agent1/feature
   git merge origin/agent2/feature
   git push origin main
   ```

3. Agents stay updated with main:
   ```
   # In agent worktree
   cd ../repo-agent1
   git fetch origin
   git merge origin/main
   ```
```

## Agent Work Agreement

### Establishing Work Boundaries

1. Define clear module/file ownership
   - Agent1: responsible for module A (e.g., authentication)
   - Agent2: responsible for module B (e.g., data processing)
   - AgentN: responsible for module X

2. Create a shared work agreement document
   - List each file/directory and its assigned agent
   - Define interfaces between components
   - Document expected inputs/outputs for each module

3. Follow directory-based separation
   - Structure project to minimize overlap between agents
   - Use separate directories for different functional areas

### Conflict Prevention Strategies

1. Regular synchronization meetings
   - Brief update on current progress
   - Discuss upcoming changes that might affect other agents
   - Resolve potential conflicts before they occur

2. Interface-first approach
   - Define and document APIs between components before implementation
   - Use test-driven development to verify interfaces
   - Create interface contracts that all agents agree to follow

3. Scheduled merges
   - Establish regular merge windows (e.g., daily or twice weekly)
   - All agents push changes before the merge window
   - Main repository manager handles merges and resolves conflicts

### Cross-Module Changes

1. When changes span multiple agent areas:
   - Document proposed changes in shared document
   - Get explicit approval from affected agents before implementation
   - Consider pair programming for critical cross-module changes

2. For API/interface changes:
   - Propose changes in advance
   - Get agreement from all impacted agents
   - Consider versioning interfaces during transition periods
